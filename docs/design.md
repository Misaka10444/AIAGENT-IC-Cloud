# 设计说明与关键决策记录

本文件记录「云梯 · 学业规划与选课顾问 Agent」的设计推理过程，特别是**为什么这样做而不是那样做**。
交付文档《项目设计与开发方案》面向评审，本文件面向后续维护者与答辩追问。

---

## 1 目标与非目标

### 1.1 目标

1. 把分散在制度文档中的选课约束，变成可执行、可解释、可回溯的计算。
2. 每个结论都能指到「哪个工具的哪次调用」或「哪份文档的哪一行」。
3. 在无网络、无密钥的赛场环境下完整运行。

### 1.2 非目标（明确不做）

| 非目标 | 原因 |
| --- | --- |
| 成绩预测与及格承诺 | 缺少历史成绩分布与考核难度数据；且此类承诺会误导学生 |
| 替代正式选课与学分认定 | 属于教务管理职权，系统只产出建议 |
| 教师评价 | 课程难度只引用公开培养方案描述，不做教师层面比较 |
| 真实个人信息处理 | 全部画像以代号承载，系统内不存在姓名/学号/联系方式字段 |
| 覆盖全校专业 | 知识库只覆盖人工智能工程技术专业 2025 版培养方案 |

非目标中的前两条由 `src/agent/safety.py` 的输入护栏强制实现，不依赖提示词自觉。

## 2 系统分层与职责

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| 接入层 | 收请求、维护会话 id | 不做业务判断 |
| 编排层 | 意图、检索、工具、校验、生成的调度 | 不直接读写数据文件 |
| 能力层 | 10 个工具，纯函数式，统一信封 | 不做自然语言生成 |
| 数据层 | 课程库、培养方案、画像、知识库 | 不含业务逻辑 |
| 可观测 | 每轮对话落盘 JSONL | 不参与决策 |

分层的实际收益：评测时可以用 `AGENT_RERANK=0` 关掉重排、用 `AGENT_AUDITOR=0` 关掉自检，
而不修改业务代码——这正是消融实验能做的原因。

## 3 技术选型与工程约束

### 3.1 Python 标准库优先

`urllib` 替代 `requests`、`http.server` 替代 Flask/FastAPI、手写 BM25 替代向量库、
手写 markdown 渲染替代前端框架。每一项的代码量都在可接受范围（检索 200 行、Web 服务 180 行），
换来的是"拿到仓库就能跑"。

### 3.2 零第三方运行时依赖

`requirements.txt` 不含第三方包。原因有三：

1. **赛场不可控**：评审或答辩现场可能断网、无 pip 源、Python 版本不一致。依赖越多，失败面越大。
2. **演示确定性**：录屏与现场演示必须一次成功，工具链环节越少越好。
3. **诚信成本**：如果核心能力依赖某个框架，就必须在文档中说明其版本与许可证，
   并且要能解释"这部分到底是你做的还是框架做的"。自实现让边界清晰。

Pillow 与 python-docx 只用于生成方案文档与插图，不进入运行时，已在 README 中明确区分。

### 3.3 自实现 BM25 而非向量检索

知识库规模是 7 篇文档、34 个片段。在这个量级上：

- 向量检索需要嵌入模型（约 100MB 权重）与向量库，收益有限；
- BM25 用字二元组即可覆盖中文专业术语，且**无需分词词典**，对"学分认定""时间冲突"这类
  复合词切分稳定；
- BM25 的分数可直接用于设定相关性阈值（见 4.2），向量余弦相似度的阈值在不同模型间不可迁移。

代价是语义泛化弱：问"选课能不能反悔"未必召回"退选"条款。这一限制已在 README 的已知限制中写明。

### 3.4 默认不用大模型

这是本项目最需要解释的决策。默认引擎是规则路由 + BM25 + 模板化生成，模型网关仅作为可选增强层。

理由：

1. **判定性任务不需要生成能力**。学分够不够、先修满不满足、时间冲不冲突，是确定性的布尔判断，
   交给工具比交给模型更准。
2. **可复现性**。同一输入恒定输出，评测数字才有意义；否则每次评测都是抽样，无法做消融对比。
3. **合规成本**。调用未报备的第三方服务需要额外说明与授权，而本地引擎不产生任何外部请求。

配置网关后，只有 **Planner 的意图分类**切换到模型；工具选路与参数构造仍由本地规则生成。
这是刻意保留的人工控制点：模型可以影响"理解"，不能影响"计算"。

### 3.5 角色拆分但不拆模型调用

五个角色（Planner / Retriever / ToolRunner / Auditor / Composer）在同一进程内以显式数据结构传递。
没有采用"多个 LLM 各自持有上下文互发消息"的方案，因为那会引入多级采样不确定性，
且延迟从毫秒级升到秒级。详见方案第 3.2 节的对比表。

## 4 检索设计

### 4.1 切分

按二级标题分节，节内以 400 字窗口、80 字重叠切分，片段保留原文起始行号。

选择章节边界而非固定长度，是因为制度条款的语义边界就是章节边界：
把"条件"与"例外"切到两个片段里，检索结果会自相矛盾。

### 4.2 阈值标定（实测）

在标定阈值之前，先测了两类问题的 Top-1 得分分布：

| 问题类型 | 样例 | Top-1 BM25 得分 |
| --- | --- | --- |
| 知识库不覆盖 | 学校食堂几点开门、学校游泳馆收费多少 | 2.96 / 2.97 |
| 知识库覆盖 | 毕业的学分要求是多少、每学期选课分几轮 | 5.49 / 11.08 |

取 **3.5**（`AGENT_MIN_SCORE`）作为分界，两侧各留约 15% 余量。
低于阈值的提问不生成答案，明确回复"没有找到依据"。

**这个阈值必须作用于原始 BM25 分，而不是重排后的总分**——重排会加分，如果按重排分设阈值，
无关提问也会被"加"进阈值内，弃答机制就失效了。代码中过滤发生在重排之前，原因即此。

### 4.3 重排

`score = BM25 + 0.8 × 标题命中率 + 0.5 × 查询覆盖率`

- 标题命中率：查询词出现在「章节名 + 文档名」中的占比
- 查询覆盖率：查询词出现在片段中的占比

权重不是调出来的最优点，而是**可解释优先**的选择：答辩时能说清"为什么这条排前面"。
实测在 25 条检索用例上 Top-1 文档命中率 84.0% → 88.0%，MRR@5 0.900 → 0.920，
章节命中率 96.0% 不变——重排改善排序，不改善召回上限。

## 5 评测口径

（与本文件同名的口径同时写在 `eval/run_eval.py` 的模块 docstring 中，两处需同步修改。）

### 5.1 两个用例集

| 用例集 | 规模 | 测什么 | 为什么分开 |
| --- | --- | --- | --- |
| `eval/cases.jsonl` | 50 条 | 端到端功能：意图、工具、引用、拒答、弃答、多轮 | 回归用 |
| `eval/retrieval_cases.json` | 25 条 | 只测检索排序（Top-1、章节命中、Recall、MRR） | 剥离工具与生成的干扰，才能单独归因重排的增益 |

### 5.2 指标定义

- **任务成功率**：单条用例的全部断言通过才算通过，分母为全部用例数。
- **意图 / 工具 / 引用准确率**：只统计设置了对应断言的子集，不把"没测"算成"没通过"。
- **幻觉率**：回答出现课程库外的课程代码，或出现"保证/包过"等承诺性表述的用例占比。
- **弃答正确率**：知识库不覆盖的问题，回答应明确"没有找到依据"。
- **延迟**：一次 `handle()` 的端到端墙钟时间，含规划、工具、检索、校验、生成。

### 5.3 一个诚实的结论

50 条功能用例在"重排+自检开启"与"全部关闭"两种配置下都是满分。
这说明该用例集**已饱和、区分度不足**，它适合做回归，不适合用作优化效果的证据。

因此本项目把"优化有前后对比"的举证责任放在检索子集上，并在评测报告中写明这一取舍，
而不是只贴一张"前后都是 100%"的表格。

## 6 已知取舍与后续优化

| 取舍 | 当前代价 | 若继续迭代 |
| --- | --- | --- |
| 规则路由而非语义模型 | 高度口语化提问的意图识别弱 | 接入网关做语义分类，保留规则兜底 |
| BM25 而非向量检索 | 语义泛化弱（"反悔"找不到"退选"） | 混合检索：BM25 + 小型嵌入模型，阈值分开标定 |
| 单专业知识库 | 跨专业提问需弃答 | 多专业培养方案，按专业路由 |
| 构造样例数据 | 数值不等于真实教务数据 | 对接教务接口（需授权与脱敏管道） |
| 单人会话记忆 | 不支持跨设备续聊 | 会话持久化到本地存储 |
